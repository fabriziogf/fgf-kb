# Product case and strategy frameworks

## Two scaffolds

**Design case** — clarify goal and scope → pick the user and segment → name the pains and
jobs to be done → set a success metric → generate solutions → prioritize by impact vs.
effort → define the MVP → metrics and risks.

**Strategy case** — goal and context → users and market → where to play and how to win →
options and trade-offs → sequencing → metrics → risks.

In both: **recommend one, don't list several.** A menu of options is an abdication.

## Frameworks worth naming

- **Jobs To Be Done** — what the user is really hiring the product to do. Design to the job, not the demographic.
- **North-star + metric tree** — one primary outcome, supported by guardrails and input metrics. See [[metric-design-and-traps]].
- **Impact vs. effort / RICE** — value over cost; RICE adds reach and confidence.
- **AARRR funnel** — acquisition, activation, retention, revenue, referral. Useful for *locating* where a problem lives before solving it.
- **Kano model** — basic, performance, and delight needs. Don't over-invest in delight before basics work.
- **Crawl-walk-run** — sequence an ambitious vision into safe, provable phases.
- **Build-measure-learn** — ship the smallest test of the *riskiest assumption*.
- **Marketplace dynamics** — liquidity, network effects, cold start. Supply and demand must grow together.
- **Moats** — network effects, switching costs, scale, brand, proprietary data.

## Product-sense principles

- Start from the user and the pain, then segment, then solve.
- State assumptions out loud; ask one or two clarifying questions before diving in.
- Recommend, don't list. Develop and defend a point of view.
- Tie every idea to a success metric and name the trade-offs.
- In two-sided products, name the impact on *both* sides every time.

The characteristic failure for a technically strong PM is under-indexing on user empathy
and jumping to the *how*. Be deliberate about starting from the user and narrating your
structure — the reasoning is what's being evaluated, not the answer.

## Structuring a product case presentation

For a case you present rather than discuss, a few things carry disproportionate weight:

- **One concrete experience artifact** beats several abstract diagrams. A believable mock of the actual experience is the most persuasive object you can put in front of a cross-functional audience — it converts a strategy claim into something people can react to.
- **Low text, high narration.** Slides anchor; you talk. Resist adding copy.
- **A clear reframe.** The best cases contain one sentence that changes how the audience sees the problem ("this is not a feature, it's a platform"; "the constraint is authority, not knowledge").
- **Name the bold calls and their trade-offs explicitly.** A "key decisions and trade-offs" section signals judgment better than any amount of analysis.
- **Size the load-bearing assumption.** If the whole argument rests on one unproven claim, put an honest, clearly-labelled estimate behind it rather than asserting it. An order-of-magnitude framing with stated assumptions is far stronger than confidence alone.
- **Assumption → how I'd test it.** Pairing each assumption with its validation makes the work legible as a plan rather than a guess.

## Deciding what not to build

Against the goal and the user pain. Say no to anything off the north star, anything that
spends trust, and anything not safe or reversible enough to start with.
